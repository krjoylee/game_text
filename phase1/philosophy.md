## 1. 근본 철학 (Fundamental Philosophy)

### 1.0 "디비나 루두스(Divina Ludus)"의 어원과 게임 탄생의 철학

#### 1. 어원적 의미 (Etymology)
* **디비나 (Divina, 라틴어 여성형 형용사)**: 
  * '신성한(Divine)', '비범한', '숭고한 영혼의 영역'을 뜻합니다.
  * 서양 문학사상 가장 거대한 구원의 서사인 **단테 알리기에리의 《신곡(La Divina Commedia)》**에서 유래했습니다. 인간의 지옥 같은 고통과 연옥의 참회를 거쳐 끝내 천국의 빛에 도달하는 문학적 숭고함을 상징합니다.
* **루두스 (Ludus, 라틴어 명사)**: 
  * '놀이(Play)', '게임(Game)', '연극 무대(Theatrical Play)', 혹은 '배움의 학교(School)'를 뜻합니다.
  * 요한 하위징아가 《호모 루덴스(Homo Ludens, 놀이하는 인간)》에서 주창했듯, 인간은 놀이를 통해 문화를 빚고 세계의 본질을 학습합니다.

#### 2. 제목 "디비나 루두스"가 탄생한 이유와 철학 (Why Divina Ludus?)
* **"인간 영혼을 밝히는 신성한 문학(Divina)을 인터랙티브한 연극 무대이자 지혜의 놀이(Ludus)로 부활시킨다"**
  1. **박제된 고전을 살아 숨 쉬는 체험으로**:
     * 수백 년 동안 인류의 지혜를 지탱해 온 고전문학은 오늘날 서가에 갇힌 채 "읽어야 하지만 아무도 끝까지 읽지 않는 두껍고 지루한 책"으로 박제되었습니다.
     * 《디비나 루두스》는 대문호들의 깊은 사색과 숭고한 영혼의 갈등(Divina)을 플레이어가 직접 대사를 읊고 결단을 내리는 '놀이의 장(Ludus)'으로 해방시키기 위해 탄생했습니다.
  2. **놀이를 통한 능동적 구원과 성찰**:
     * 독자는 더 이상 수동적인 관객이 아닙니다. 플레이어는 단테가 되어 지옥의 유혹을 뿌리치고, 싱클레어가 되어 알을 깨는 투쟁을 벌이며, 조지 오웰의 농장에서 비판적 양심을 지킬 것인지 결단합니다.
     * 즉, **"놀이(Ludus)라는 가장 가볍고 즐거운 형식을 통해, 신성한 지혜(Divina)라는 가장 깊고 묵직한 영혼의 울림을 전한다"**는 역설적 미학이 바로 이 이름의 정체성입니다.
  3. **팩(Pack) 교체형 요술 냄비 엔진**:
     * 옛날 패미컴 롬팩에 팩을 갈아 끼우며 새로운 세계로 모험을 떠났듯, 엔진 코드는 1바이트의 군더더기 없이 단단한 무대로 남고(Ludus), 그 위에 단테·헤세·오웰·로알드 달 등 인류의 고전 팩(Divina)을 꽂아 무한한 문학 우주를 탐험하는 영구 불멸의 플랫폼을 지향합니다.

### 1.1 우리가 만드는 것 — 두 개의 독립 엔진 체계

우리의 생태계는 **서로 다른 책임을 가진 2개의 완전히 분리된 엔진**으로 구성됩니다:

```
│ 1. Divina Ludus (게임 엔진 / 런타임 플레이어)                │
│    • 책임: YAML 팩을 읽어 터미널 5영역 화면에 렌더링하고     │

│    • 기술: Pure Rust (Zero Dependency, 1MB 이하 정적 바이너리) │
└──────────────────────────────▲──────────────────────────────┘
                               │ 팩 카트리지 주입 (YAML)
┌──────────────────────────────┴──────────────────────────────┐
│ 2. AsciiArt Studio (이미지/아트 생성 엔진 / 제작 툴체인)     │
│    • 책임: 원작 삽화/그림/AI 이미지를 분석하여 74x14 규격의  │
│           고밀도 아스키 아트로 자동 변환·생성하는 저작 엔진 │
│    • 기술: Python + OpenCV / Pillow + Canny Edge 필터       │
└─────────────────────────────────────────────────────────────┘
```

| 구분 | 🎮 게임 엔진 (`Divina Ludus`) | 🎨 이미지 생성 엔진 (`AsciiArt Studio`) |
|------|-------------------------------|------------------------------------------|
| **정체성** | 런타임 플레이어 (Player / VM) | 저작 및 콘텐츠 생성 도구 (Authoring Tool) |
| **입력** | `4_game_scene.yaml` (팩 데이터) | 원본 이미지 (PNG/JPG, 일러스트, AI 그림) |
| **출력** | 터미널 게임 화면 및 인터랙션 | `74 x 14` 고밀도 아스키 아트 YAML 스니펫 |
| **목표** | 초경량, 무의존성, 무결점 고정 프레임 | 압도적인 명암비, 선명한 엣지(외곽선), 미적 완성도 |

### 1.2 핵심 원칙 (Core Principles)

1. **문학은 이미 완성되어 있다** — 엔진은 원작을 훼손하지 않는다. 씬을 나누고 선택지를 붙이되, 서사의 순서와 메시지는 원작 그대로 보존한다.
2. **팩은 카트리지다** — 고전 게임기에 카트리지를 꽂듯, JSON/YAML 팩 하나만 바꾸면 완전히 다른 게임이 된다. 엔진 코드는 건드리지 않는다.
3. **쉬움이 정의다** — 팩을 만드는 데 프로그래밍 지식이 필요 없다. 문학을 사랑하는 사람이라면 누구나 자기가 좋아하는 작품을 게임으로 만들 수 있어야 한다.
4. **대문호의 이름이 브랜드다** — 단테, 헤세, 톨스토이... 작가의 이름만으로 세계관이 확장된다. 각 팩은 그 작가만의 색깔을 오롯이 담는다.
5. **기록은 한글과 목적 중심이다 (Git Commit Rule)** — 모든 버전 관리(Git 커밋)는 **반드시 한국어로 작성**하며, 단순 동작 나열이 아닌 **"무엇이 안 되어서(Problem/Why) 무엇을 해결했는가(Purpose/Solution)"**의 인과관계를 명확히 남긴다.

### 1.3 한 줄 비전

> *"세계의 모든 고전 문학이 하나의 엔진 위에서 게임이 된다."*

## 2. 세계 확장 (World Expansion)

### 2.1 팩은 완전 독립이다

각 팩은 **별개의 게임**이다. 팩 사이에 진행도 연동, 크로스오버, 공유 세계관은 없다.
이유는 단순하다: **원작이 서로 다른 세계이므로, 게임도 서로 다른 세계여야 한다.**

```
Divina Ludus Engine
    │
    ├── 📖 단테 · 신곡 천국편       ← 팩 A (서사시)
    ├── 📖 헤세 · 데미안            ← 팩 B (성장소설)
    ├── 📖 톨스토이 · 단편집         ← 팩 C (옴니버스)
    ├── 📖 카프카 · 변신            ← 팩 D (부조리)
    ├── 📖 생텍쥐페리 · 어린왕자    ← 팩 E (우화)
    ├── 📖 도스토예프스키 · 죄와 벌  ← 팩 F (심리극)
    └── ...무한 확장
```

### 2.2 확장의 3단계

| 단계 | 전략 | 예시 |
|------|------|------|
| **Seed (씨앗)** | 개발팀이 3개 레퍼런스 팩을 직접 제작하여 엔진의 범용성을 증명 | 단테 · 헤세 · 톨스토이 |
| **Garden (정원)** | 오픈 포맷 공개 + 팩 제작 가이드 배포로 커뮤니티 참여 유도 | 카프카, 셰익스피어, 한국 고전 등 |
| **Forest (숲)** | 커뮤니티가 자생적으로 팩을 만들고 공유하는 생태계 완성 | 팩 마켓플레이스, 큐레이션 |

### 2.3 레퍼런스 팩 3종 — 왜 이 조합인가

이 세 작품은 **문학의 서로 다른 구조**를 대표한다. 이 셋이 모두 같은 엔진에서 돌아간다면, 엔진의 범용성은 증명된 것이다.

#### 📖 팩 A: 단테 알리기에리 — 신곡 · 천국편 (Paradiso)

| 항목 | 내용 |
|------|------|
| **장르** | 서사시 / 신학적 순례 |
| **서사 구조** | **선형 상승** — 제1천(월구) → 제10천(황림천)으로 단계적 상승 |
| **핵심 관계** | 단테 ↔ 베아트리체 (인도자/스승) |
| **팩 고유 수치** | `영혼의 빛 (Light of Soul)` — 올바른 이해 시 밝아짐 |
| **실패의 의미** | 빛에서 멀어짐 → 이전 천으로 회귀 |
| **테마 색깔** | 신성, 질서, 상승, 빛 |

#### 📖 팩 B: 헤르만 헤세 — 데미안 (Demian)

| 항목 | 내용 |
|------|------|
| **장르** | 성장소설 (Bildungsroman) |
| **서사 구조** | **내면 성장** — 밝은 세계 → 어두운 세계 → 통합(아브락사스) |
| **핵심 관계** | 싱클레어 ↔ 데미안 (그림자/반쪽/각성자) |
| **팩 고유 수치** | `자아의 각성 (Awakening)` — 진정한 자아에 다가갈수록 상승 |
| **실패의 의미** | 기존 세계(안전한 거짓)에 안주 → 성장 멈춤 |
| **테마 색깔** | 이원성, 자아, 파괴와 재생, 알 깨기 |

#### 📖 팩 C: 레프 톨스토이 — 사람은 무엇으로 사는가 (단편 모음)

| 항목 | 내용 |
|------|------|
| **장르** | 도덕 우화 / 단편집 |
| **서사 구조** | **에피소드 선택** — 독립적 단편들을 자유 순서로 진행 |
| **핵심 관계** | 천사/관찰자 ↔ 인간 군상 (다양한 인물들) |
| **팩 고유 수치** | `인간애의 깊이 (Depth of Humanity)` — 타인을 이해할수록 상승 |
| **실패의 의미** | 이기심에 빠짐 → 깨달음 없이 이야기가 끝남 |
| **테마 색깔** | 사랑, 겸손, 소박한 진리, 일상의 성스러움 |

### 2.4 이 조합이 증명하는 것

```
단테 (선형 상승)  →  엔진이 "레벨 진행형 구조"를 지원함을 증명
헤세 (내면 성장)  →  엔진이 "분기/변화형 구조"를 지원함을 증명
톨스토이 (에피소드) →  엔진이 "독립 에피소드형 구조"를 지원함을 증명
```

**세 가지 서사 구조를 모두 커버하면, 세상의 거의 모든 문학을 게임화할 수 있다.**

## 3. 팩 시스템 설계 철학 (Pack System Philosophy)

### 3.1 팩이란 무엇인가

팩(Pack)은 **하나의 문학 작품을 게임으로 만든 데이터 묶음**이다.
JSON 또는 YAML 파일들의 모음이며, 엔진 코드와 완전히 분리되어 있다.

```
packs/
├── paradiso/                    # 단테 · 신곡 천국편
│   ├── pack.yaml                # 팩 설정 (이것 하나가 게임의 정체성)
│   └── scenes/                  # 씬 데이터들
│       ├── chapter_01_scene_01.yaml
│       ├── chapter_01_scene_02.yaml
│       └── ...
├── demian/                      # 헤세 · 데미안
│   ├── pack.yaml
│   └── scenes/
└── tolstoy_stories/             # 톨스토이 · 단편집
    ├── pack.yaml
    └── scenes/
```

### 3.2 팩의 핵심: `pack.yaml` — 이것 하나로 게임이 정의된다

팩 제작자가 작성하는 **단 하나의 설정 파일**. 
여기에 세계의 이름, 철학, 수치, 구조를 선언하면 엔진이 나머지를 처리한다.

```yaml
# ============================================
# pack.yaml — 팩 정의 파일
# 이 파일 하나로 게임의 정체성이 결정된다
# ============================================

# --- 기본 정보 ---
id: "paradiso"
title: "신곡 — 천국편"
author: "단테 알리기에리"
description: "10개의 천을 순례하며 신성한 빛에 다가가는 여정"
language: "ko"

# --- 문체 설정 ---
tones:
  casual:
    name: "현대 구어체"
    description: "친근하고 쉽게 읽히는 대화체"
  classic:
    name: "고전 번역체"
    description: "원전의 숭고함과 무게감을 보존하는 장엄한 문체"
  default: "casual"

# --- 세계관 핵심 명칭 (이것이 게임의 철학을 결정한다) ---
world:
  # 핵심 수치 — 이름만 바꾸면 다른 세계가 된다
  metric:
    name: "영혼의 빛"
    name_en: "Light of Soul"
    icon: "◆"
    max: 10
    initial: 3
    description: "올바른 이해를 할수록 밝아지고, 잘못된 선택 시 흐려진다"

  # 챕터 단위 명칭
  chapter_term: "천"           # 단테: "천", 헤세: "장", 톨스토이: "이야기"
  chapter_term_en: "Heaven"

  # 실패/회귀 설정
  failure:
    speaker: "beatrice"
    message_key: "fail_message"  # 씬 JSON의 substitution 키 참조
    return_strategy: "chapter_start"  # chapter_start | scene_retry | game_over

  # 암호(패스워드) 시스템
  password:
    enabled: true
    description: "각 천 도달 시 핵심 키워드를 암호로 부여"

# --- 서사 구조 ---
structure:
  type: "linear"               # linear(선형) | growth(성장분기) | episodic(에피소드)
  chapters:
    - id: "heaven_01"
      name: "월구 (Moon)"
      password: "피카르다"
      scenes: ["heaven_01_scene_01", "heaven_01_scene_02"]
    - id: "heaven_02"
      name: "수성 (Mercury)"
      password: "유스티니아누스"
      scenes: ["heaven_02_scene_01"]
    # ... 제10천까지

# --- 플레이 모드 ---
modes:
  full:
    name: "전체 정독 모드"
    description: "10개 천 전체를 순례하며 원작 완독에 준하는 경험"
    chapters: "all"
  quick:
    name: "핵심 요약 모드"
    description: "핵심 5개 천만 압축 선별"
    chapters: ["heaven_01", "heaven_03", "heaven_05", "heaven_08", "heaven_10"]
  demo:
    name: "맛보기 모드"
    description: "2~3개 씬만 오픈"
    chapters: ["heaven_01"]

# --- 캐릭터 정의 ---
characters:
  protagonist:
    id: "dante"
    name: "단테"
    icon: "♦"
  guide:
    id: "beatrice"
    name: "베아트리체"
    icon: "☽"

# --- 카드 프레임 템플릿 ---
card_template:
  header: "│                  {chapter_term}{chapter_num} · {chapter_name}"
  # 나머지는 씬 데이터에서 정의
```

### 3.3 팩을 만드는 것은 이 질문에 답하는 것이다

팩 제작자가 `pack.yaml`을 작성할 때 답해야 하는 질문은 **딱 6가지**:

```
1. 어떤 작품인가?              → title, author, description
2. 핵심 수치의 이름은?          → world.metric.name ("영혼의 빛", "자아의 각성", ...)
3. 챕터를 뭐라 부르나?          → world.chapter_term ("천", "장", "이야기", ...)
4. 실패하면 어떻게 되나?        → world.failure.return_strategy
5. 이야기 구조는?              → structure.type (linear / growth / episodic)
6. 등장인물은 누구인가?         → characters
```

**나머지는 전부 기본값이 있다.** 극단적으로, 위 6가지만 채우고 씬 파일만 작성하면 게임이 된다.

### 3.4 데미안 팩은 이렇게 달라진다 (예시)

```yaml
id: "demian"
title: "데미안"
author: "헤르만 헤세"

world:
  metric:
    name: "자아의 각성"
    name_en: "Awakening"
    icon: "◈"
    max: 10
    initial: 1
    description: "진정한 자아에 다가갈수록 상승한다"

  chapter_term_en: "Chapter"

  failure:
    speaker: "demian"
    message_key: "fail_message"
    return_strategy: "scene_retry"

      scenes: ["ch01_scene_01", "ch01_scene_02"]
    - id: "ch_02"

      scenes: ["ch02_scene_01"]
    # ...

    id: "sinclair"
```

**pack.yaml만 바꿨을 뿐인데, 완전히 다른 게임이 된다.**

## 4. 엔진이 담당하는 것 vs 팩이 담당하는 것

### 4.1 책임 분리 원칙

엔진은 **"어떻게 보여줄까"**를 담당하고, 팩은 **"무엇을 보여줄까"**를 담당한다.

```
┌──────────────────────────────────────────────────┐
│              Divina Ludus Engine                  │
│                                                  │
│  ┌────────────────────────────────────────────┐  │
│  │  항상 동일 (팩이 바뀌어도 변하지 않음)        │  │
│  │                                            │  │
│  │  • 카드 북 프레임 렌더링                     │  │
│  │  • 키 입력 처리 (번호 선택)                  │  │
│  │  • 화면 전환 (Clear Screen)                 │  │
│  │  • 수치 게이지 바 표시                       │  │
│  │  • 암호 입력/검증 시스템                     │  │
│  │  • 톤 전환 (구어체/고전체)                   │  │
│  │  • 씬 JSON/YAML 파싱 & 템플릿 치환          │  │
│  │  • 진행 구조 해석 (linear/growth/episodic)   │  │
│  │  • 실패/회귀 로직 실행                       │  │
│  │  • 최종 결과 화면 생성                       │  │
│  └────────────────────────────────────────────┘  │
│                                                  │
│  ┌────────────────────────────────────────────┐  │
│  │  팩에서 읽어옴 (팩마다 달라짐)               │  │
│  │                                            │  │
│  │  • 작품 제목, 작가, 설명                     │  │
│  │  • 수치 이름, 아이콘, 초기값, 최대값          │  │
│  │  • 챕터 구조와 씬 순서                       │  │
│  │  • 캐릭터 이름과 아이콘                      │  │
│  │  • 대사 텍스트 (구어체/고전체 이중)           │  │
│  │  • 선택지 텍스트와 수치 변화량                │  │
│  │  • 아스키 아트 카드 이미지                    │  │
│  │  • 실패 시 대사와 복귀 지점                   │  │
│  │  • 챕터별 암호 키워드                        │  │
│  │  • 엔딩 성향 유형 정의                       │  │
│  └────────────────────────────────────────────┘  │
│                                                  │
└──────────────────────────────────────────────────┘
```

### 4.2 엔진의 3가지 진행 모드

엔진은 `structure.type` 값에 따라 세 가지 방식으로 게임을 진행한다.
팩 제작자는 이 중 하나만 선택하면 된다.

| 모드 | `structure.type` | 동작 | 대표 작품 |
|------|-----------------|------|----------|
| **선형 (Linear)** | `linear` | 챕터를 순서대로 진행. 이전 챕터 클리어 없이 다음 챕터 불가 | 단테 신곡 |
| **성장 (Growth)** | `growth` | 기본은 순차이지만, 선택에 따라 일부 챕터가 열리거나 닫힘 | 헤세 데미안 |
| **에피소드 (Episodic)** | `episodic` | 챕터 목록에서 자유 선택. 순서 없음. 개별 완결 | 톨스토이 단편 |

### 4.5 팩 제작 파이프라인 (Pack Creation Pipeline)

이 섹션에서는 팩을 생성하기 위한 표준 4단계 프로세스를 설명합니다:

1. **원문(Story)** → 원작 텍스트를 게임용으로 정리 (1_story.md)
2. **콘티(Storyboard)** → 씬 분할, 아스키 아트, 대사 배치 (2_conti.md)
3. **씬(Scene Draft)** → 엔진이 읽는 데이터 초안 (3_scene.yaml)
4. **게임 씬(Game Scene)** → 확장 화면 레이아웃 적용한 정식 버전 (4_game_scene.yaml)

이 4단계 파이프라인은 모든 팩 제작의 표준이며, 이러한 구조를 통해 품질과 추적성을 보장합니다.

### 4.6 LLM 기반 팩 생성 도구 (AI-Assisted Pack Creation)

이 섹션에서는 팩 생성을 자동화하는 LLM 기반 도구의 비전을 설명합니다:

- **목표**: 문학을 사랑하지만 기술이 없는 사람도 팩을 만들 수 있게
- **형태**: MCP 서버 또는 Skill 형태로 제공
- **워크플로우**:
  1. 사용자가 원문(소설/시/설화)을 제공
  2. 사용자가 핵심 설정을 결정 (수치 이름, 캐릭터, 구조 타입 등 6가지 질문)
  3. LLM이 원문 → 콘티 → 씬 → 게임씬을 자동 생성
  4. 사용자가 검토/수정 후 완성
- **핵심 원칙**: LLM은 보조 도구일 뿐, 최종 승인은 반드시 사람이 한다
- **검증**: `is_interpreted` 태그가 있는 씬은 반드시 사람이 확인

이러한 도구를 통해 'Forest (숲)' 확장 단계가 현실성을 가지며, 커뮤니티가 실제로 팩을 직접 제작할 수 있게 됩니다.

## 5. 방향성 (Direction)

### 5.1 지금 만드는 것 (Phase 1)

```
목표: Rust 엔진 + 3개 레퍼런스 팩으로 범용성 증명

         엔진 (Rust)
         ┌─────────┐
         │ Renderer │──── 카드 프레임 렌더링
         │ Input    │──── 선택지 입력 처리
         │ State    │──── 게임 상태 관리
         │ Loader   │──── 팩 YAML/JSON 로딩
         └─────────┘
              │
    ┌─────────┼─────────┐
    ▼         ▼         ▼
  단테팩    데미안팩   톨스토이팩
 (linear)  (growth)  (episodic)
```

### 5.2 나중에 만드는 것 (Phase 2+)

| Phase | 목표 |
|-------|------|
| **Phase 2** | HTML5/JS 웹 버전 (동일 팩 데이터 재사용) |
| **Phase 3** | 팩 제작 가이드 & 템플릿 공개 |
| **Phase 4** | 커뮤니티 팩 공유 플랫폼 |
| **Phase 5** | 수익화 — 프리미엄 팩 / 맛보기→전체 전환 |

### 5.3 절대 하지 않는 것 (Anti-Patterns)

1. **원작을 훼손하지 않는다** — 게임화를 위해 원작의 서사를 왜곡하거나 재배열하지 않는다.
2. **엔진에 팩 종속 코드를 넣지 않는다** — "단테용 특수 로직" 같은 것은 존재하지 않는다.
3. **팩 간 의존성을 만들지 않는다** — 각 팩은 완전 독립. 다른 팩의 존재를 가정하지 않는다.
4. **팩 제작을 어렵게 만들지 않는다** — YAML 6개 항목만 채우면 게임이 만들어진다.
