## 1. 개요: 복잡함을 없애는 황금 공식

텍스트 게임을 만들 때 가장 흔히 저지르는 실수는 **"스토리의 모든 분기를 코드(`if/else`)로 짜는 것"**입니다. 그렇게 하면 대사 하나 바꿀 때마다 코드를 다시 컴파일해야 하고, 버그가 생기기 쉽습니다.

Divina Ludus는 다음의 황금 공식을 따릅니다:

$$\text{엔진 (Rust)} + \text{데이터 (YAML)} = \text{게임}$$

* **엔진 (Rust)**: 멍청할 정도로 단순한 기계 (틀 그리기 + 번호 입력받기 + 가방 넘기기).
* **데이터 (YAML)**: 작품의 모든 것 (대사, 그림, 선택지, 점수 계산, 분기).

## 2. 복잡함을 단순하게 만드는 5대 실전 기술

### 🎯 1. "빵틀과 반죽" — 데이터 주도 설계 (Data-Driven Design)

* **복잡한 방식 (안 좋은 예)**:
  * "1번 누르면 놀부가 화내고, 2번 누르면 흥부가 운다"를 Rust 코드로 일일이 작성.
  * 새로운 소설(데미안, 톨스토이)을 넣으려면 게임 엔진 코드를 전부 뜯어고쳐야 함.
* **우리의 실전 기술**:
  * 엔진 코드는 "어떤 씬이든 상관없이 **현재 씬 데이터를 읽어 화면에 띄우고, 선택된 번호의 `next_scene`으로 이동한다**"는 단 하나의 규칙만 가집니다.
  * 흥부놀부전이든, 데미안이든, 단테 신곡이든 **YAML 파일만 갈아끼우면 엔진은 수정할 필요가 없습니다.**

```
[YAML 팩 (반죽)] ──(장착)──> [Rust 엔진 (빵틀)] ──> [완성된 게임]
```

### 🕳️ 2. "빈칸 채우기" — 템플릿 치환 (Placeholder Substitution)

* **복잡한 방식 (안 좋은 예)**:
  * 구어체용 아스키 화면, 고전체용 아스키 화면, 영어용 아스키 화면을 따로따로 그림.
  * 오타나 대사 한 줄 수정할 때마다 아스키 그림 전체가 깨져서 다시 그려야 함.
* **우리의 실전 기술**:
  * 아스키 아트 안에는 뼈대만 두고 `{nolbu_line}`, `{virtue_bar}`처럼 **구멍(변수)**만 뚫어둡니다.
  * 화면을 그리는 순간, 엔진이 현재 선택된 문체(구어체/고전체)에 맞춰 대사를 쏙 끼워 넣습니다.

```yaml
# 1) 아스키 그림 틀 (영구 보존)
scene_art:
  - "│  凸 \"{nolbu_line}\"  │"

# 2) 갈아끼우는 대사 데이터
substitutions:
  tone_casual:
    nolbu_line: "썩 나가!"
  tone_classic:
    nolbu_line: "썩 물러가라!"
```

### 🎒 3. "여행 가방 하나로 끝내기" — 단일 상태 객체 (GameState Pattern)

* **복잡한 방식 (안 좋은 예)**:
  * "현재 체력", "현재 위치", "이전 선택지", "문체 설정" 등 수십 개의 변수를 프로그램 곳곳에 따로따로 분산 관리하다가 변수 간 충돌 발생.
* **우리의 실전 기술**:
  * 게임 진행에 필요한 모든 정보를 `GameState`라는 **단 하나의 가방(구조체)**에 모아둡니다.

```rust
// 게임의 모든 기억이 들어있는 단 하나의 가방
struct GameState {
    current_scene_id: String,  // 현재 위치 (예: "act01_scene_01")
    metric_value: i32,         // 현재 수치 (예: 5)
    current_tone: String,      // 현재 문체 (예: "casual")
    history: Vec<ChoiceRecord> // 지금까지의 선택 기록 (엔딩 분석용)
}
```

* 플레이어가 1번을 선택하면:
  1. 가방 안의 `metric_value`에 점수를 더하고,
  2. `current_scene_id`를 다음 씬 이름으로 바꾼 뒤,
  3. 화면을 새로고침합니다. (스파게티 코드가 생길 틈이 없음)

### 📐 4. "한글 칼각 맞춤기 & 2D 화면 그리드 버퍼" — ScreenBuffer & Display Width

* **터미널 프로그래밍의 최대 난제**:
  * 영어/숫자는 1칸(`a`, `1`), 한글/한자/특수문자는 2칸(`흥`, `♧`), 블록 게이지(`█`, `░`)는 1칸을 차지합니다.
  * 단순히 문자열을 이어 붙여서 `println!`으로 출력하면, 텍스트가 조금만 길어져도 우측 테두리(`║`)가 밀려나며 화면 전체가 와장창 무너집니다.
* **우리의 실전 기술 (터미널 Multiplexer 방식)**:
  * **2D 가상 화면 버퍼 (`ScreenBuffer[30][78]`)**: 메모리에 `78 x 30` 크기의 가상 픽셀 판을 먼저 만들어 테두리 틀을 영구 고정합니다.
  * 텍스트(한글 대사, 아스키 그림)를 올릴 때 글자 폭을 계산하여 지정된 사각 영역 안의 좌표`(x, y)`에만 안전하게 덮어씁니다.
  * 텍스트가 아무리 길어도 **우측 테두리 좌표(Col 77)를 물리적으로 침범할 수 없으므로 틀 깨짐이 100% 원천 차단**됩니다.
  * **ANSI 절대 커서 제어(`\x1b[H`)**: 매번 화면을 지우고 스크롤하는 대신, 화면 좌상단으로 커서를 올려 고정 프레임 위에서 텍스트만 즉시 덮어씌워 **화면 깜빡임(Flicker)이 0%**가 됩니다.

### 🧱 5. "레고 블록 조립" — 5영역 화면 분할 (Region Layout)

* **복잡한 방식 (안 좋은 예)**:
  * 전체 화면 30줄을 하나의 긴 문자열로 합쳐서 출력. 대사 한 줄 길어지면 상태창이나 선택지 위치가 밀려서 무너짐.
* **우리의 실전 기술**:
  * 화면을 5개의 독립된 레고 블록으로 완전히 분리하여 각각 렌더링한 뒤 2D 버퍼에 배치합니다.

```
╔════════════════════════════════════════════════════════════════════════════╗
║ 1. HEADER (Row 0..2) : 팩 제목 + 막/씬 이름 (Row 1)                        ║
╠════════════════════════════════════════════════════════════════════════════╣
║ 2. SCENE (Row 3..16) : 아스키 아트 배경 + 화자 형상 (14줄)                 ║
╠══════════════════════════════════════════╤═══════════════════════════════╣
║ 3. DIALOGUE (Row 18..24, Col 2..41, 7줄) │ 4. STATUS (Row 18..24, 7줄)   ║
║    화자별 대화 텍스트 (스마트 줄바꿈)    │    수치 게이지, 진행도, 문체   ║
╠══════════════════════════════════════════╧═══════════════════════════════╣
║ 5. CHOICE (Row 25..29) : 번호 선택지 + 입력 프롬프트                       ║
╚════════════════════════════════════════════════════════════════════════════╝
```

* 대화가 길어지거나 바뀌어도 우측의 상태창(STATUS)이나 상단의 그림(SCENE)에 아무런 영향을 주지 않습니다.

## 🛡️ 3. 재발 방지를 위한 실전 코딩 수칙 (Lessons Learned)

다음 개발 작업 시 동일한 버그가 재발하지 않도록 반드시 지켜야 할 **4대 안전 수칙**입니다:

### 1️⃣ 입력 스트림 락(Lock) 중복 획득 금지 (Deadlock 방지)
* **문제였던 패턴**: 루프 상위에서 `io::stdin().lock()`을 들고 있는 상태에서, 하위 헬퍼 함수(`wait_for_enter`)가 또 `io::stdin().lock()`을 호출하여 교착상태 발생.
* **올바른 수칙**:
  * 단순 콘솔 앱에서는 매 입력마다 `io::stdin().read_line(&mut buffer)`을 직접 호출합니다.
  * 중첩 락이나 함수 간 락 공유를 피하고, 락의 수명을 1개 라인 읽기로 극도로 제한합니다.

### 2️⃣ 상태 키(Key) 접두사 불일치 방지 (Prefix Normalization)
* **문제였던 패턴**: YAML 헤더는 `casual`, 본문 맵은 `tone_casual`로 접두사가 엇갈려 HashMap 조회 실패.
* **올바른 수칙**:
  * 엔진 로직에서 조회할 때 `tone.trim_start_matches("tone_")`와 `format!("tone_{}", tone)` **양방향 폴백 조회**를 기본으로 지원합니다.
  * 팩 작성자가 `casual`로 쓰든 `tone_casual`로 쓰든 엔진이 유연하게 흡수하도록 방어 코드를 작성합니다.

### 3️⃣ CJK 터미널 정렬 시 format!(`{:<20}`) 절대 사용 금지
* **문제였던 패턴**: Rust 기본 포맷터 `{:<20}`은 유니코드 글자 수를 셀 뿐 표시 폭을 모르기 때문에 한글 표가 완전히 뭉개짐.
* **올바른 수칙**:
  * 터미널 표 출력에는 항상 자체 `pad_right(&str, display_width)`와 `pad_center(&str, display_width)`를 사용합니다.

### 4️⃣ 입력 처리 시 제어 명령어(q, h) 최우선 분기
* **문제였던 패턴**: 전환 씬(`is_transition`) 체크가 맨 앞에 있어서 사용자가 `q`를 눌러도 종료되지 않고 다음 장면으로 넘어가버림.
* **올바른 수칙**:
  * 모든 입력 핸들러는 **[종료 'q'/'quit'] ➔ [도움말 'h'/'help'] ➔ [전환 씬 AnyKey] ➔ [숫자 선택지]** 순서로 분기합니다.

## 4. 비개발자를 위한 필수 프로그래밍 용어 사전

| 용어 | 뜻과 비유 | 본 프로젝트에서의 역할 |
|------|-----------|------------------------|
| **Struct (구조체)** | 여러 정보를 하나로 묶어놓은 **서식/양식지** | `PackMeta`, `Scene`, `Choice`처럼 YAML 데이터를 담을 틀 |
| **Deadlock (교착상태)** | 서로가 끝나기를 기다리며 **프로그램이 멈춰버리는 현상** | stdin lock 중복 획득으로 발생했던 멈춤 현상 |
| **Display Width (표시 폭)** | 글자가 화면에서 차지하는 **실제 칸수** | 영문 1칸, 한글 2칸, 블록 게이지 1칸 계산 |
| **Word Wrap (단어 줄바꿈)** | 폭이 좁은 영역에서 문장이 넘치지 않게 **다음 줄로 넘기는 기술** | 좌측 40칸 대화창에서 대사 잘림 방지 |
| **State Machine (상태 머신)** | 정해진 규칙에 따라 **현재 상태에서 다음 상태로 전이**하는 논리 구조 | 씬 1 → 선택지 선택 → 점수 반영 → 씬 2 이동 |

## 5. 요약

이 기술들의 핵심은 **"복잡한 로직은 단순한 데이터(YAML)로 몰아넣고, 코드는 단순하고 튼튼한 틀로 유지하며, 방어적인 입력/출력 규칙을 준수한다"**는 것입니다. 프로그래밍 지식이 없어도 이 원리만 이해하면 누구나 버그 없이 안정적인 고전문학 텍스트 게임 팩을 제작할 수 있습니다.
