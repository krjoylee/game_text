## 1. 프로젝트 목표

- 고전 문학 한 권을 **통째로 게임화**하여, 게임을 클리어하면 원작을 완독한 것과 동등한 이해와 여운을 제공한다.
- **1MB 이하**의 극한 용량 제한 내에서 터미널 텍스트 게임으로 구현한다.
- **팩(Pack) 교체만으로 다른 게임이 되는 범용 엔진**을 만든다. 엔진 코드에 특정 작품 종속 로직은 없다.
- **누구나 팩을 만들 수 있는 오픈 포맷**: YAML/JSON으로 6가지 핵심 항목만 채우면 게임이 된다.
- **원작 파괴 금지**: 원작의 서사 순서와 핵심 메시지를 충실히 따르며, 개인의 해석이 필요한 부분은 반드시 기획자(사용자)의 승인을 거친다.

## 2. 핵심 설계 결정 사항 (Grill-me 인터뷰 결과)

### 2.1 조작 방식 (인터랙션)

| 결정 | 내용 |
|------|------|
| **기본 방식** | 번호 선택지 (비주얼 노벨 타입) |
| **감성 보강** | 선택지 문구에 인물의 내면 상태·사색의 방향을 반영하는 키워드형 어조를 녹여냄 |
| **예시** | `1. 베아트리체의 미소 뒤에 숨은 의미를 되새긴다` / `2. 타오르는 불빛 속에서 신성한 질서를 갈망한다` |

### 2.2 화면 구성 (UI 레이아웃)

| 결정 | 내용 |
|------|------|
| **레이아웃** | 카드 북 프레임 (아스키 아웃라인으로 화면 전체를 감싸는 고정 프레임) |
| **씬 단위 페이지네이션** | 화면 전환 시 이전 화면을 완전히 지우고(Clear Screen) 새 씬만 표시 |
| **1씬 = 1이야기 = 1주제 = 1메시지** | 독자가 씬 구분을 명확히 인지할 수 있도록 엄격한 단일 주제 원칙 적용 |

### 2.3 아스키 이미지 활용

| 결정 | 내용 |
|------|------|
| **배치 방식** | 통합 카드형 - 카드 프레임 안에 아스키 배경 + 화자 형상 + 대화 텍스트가 **하나의 씬 이미지**로 결합 |
| **역할** | 단순 장식이 아닌 **힌트 / 단서** 역할 수행 |
| **텍스트 최소화** | 장황한 묘사를 배제하고 **대화(Dialogue) 중심**, 화자의 아스키 형상 옆에 대사가 텍스트 대치(substitution) 형태로 삽입 |
| **화자 표현** | 단테와 베아트리체(또는 해당 천계의 영혼)가 아스키 캐릭터로 카드 내에 시각적으로 존재 |

### 2.4 서사 구조 — 3가지 진행 타입 (팩에서 선택)

| 타입 | `structure.type` | 동작 | 대표 작품 |
|------|-----------------|------|----------|
| **선형 (Linear)** | `linear` | 챕터를 순서대로 진행. 이전 챕터 클리어 필수 | 단테 · 신곡 |
| **성장 (Growth)** | `growth` | 기본 순차 + 선택에 따라 일부 챕터 분기 | 헤세 · 데미안 |
| **에피소드 (Episodic)** | `episodic` | 챕터 목록에서 자유 선택. 개별 완결 | 톨스토이 · 단편집 |

> **팩 제작자는 위 3가지 중 하나만 선택하면 된다. 엔진이 나머지를 처리한다.**

### 2.5 플레이 모드 (수익화 확장 대비)

| 모드 | 설명 |
|------|------|
| **전체 정독 모드 (Full Campaign)** | 10개 천 전체를 순례하며 원작 완독에 준하는 경험 제공 |
| **핵심 요약 모드 (Quick Campaign)** | 핵심 5개 천만 압축 선별하여 빠르게 진행 |
| **맛보기 모드 (Demo)** | 2~3개 씬만 오픈하여 무료 체험 / 유료 전환 유도 |

### 2.6 플레이 메커니즘 (클리어 / 실패) — 팩 정의형

| 결정 | 내용 |
|------|------|
| **핵심 수치** | 팩의 `world.metric`에서 정의. 이름, 아이콘, 최대/초기값 모두 팩이 결정 |
| **수치 예시** | 단테: `영혼의 빛 ◆`, 헤세: `자아의 각성 ◈`, 톨스토이: `인간애의 깊이 ♥` |
| **실패 시** | 팩의 `world.failure.return_strategy`에 따라 동작 (chapter_start / scene_retry / game_over) |
| **아스키 연동** | 수치에 따라 상단 아스키 이미지의 밝기/디테일이 변화 |

### 2.7 묵상의 궤적 (Trajectory of Contemplation)

| 결정 | 내용 |
|------|------|
| **선택 기록** | 플레이어가 매 씬에서 내린 모든 선택과 결과를 내부적으로 기록 |
| **최종 결과 화면** | 제10천 도달 시, 전체 여정의 선택 히스토리와 영혼 정화 상태를 종합하여 표시 |
| **목적** | "나는 어떤 의심을 품었고 어떻게 극복했는가"를 돌아보며 깊은 여운과 만족감 제공 |

### 2.8 문체 이중화 (Dual Tone Script)

| 결정 | 내용 |
|------|------|
| **메인 톤 (기본)** | 현대 한국어 구어체 - "저기 보이는 것들... 환영이야 아니면 진짜 영혼이야?" 처럼 친근하고 쉽게 읽히는 대화체 |
| **서브 톤 (전환 가능)** | 고전 번역체 - "그대여, 이 빛을 보라. 주께서 내리신 은총이 무한하도다." 처럼 원전의 숭고함과 무게감을 보존하는 장엄한 문체 |
| **이중화 목적** | 원작 훼손 논란 방지. 구어체로 접근성을 높이되, 고전체를 병행하여 원전의 격조를 언제든 확인할 수 있도록 함 |
| **전환 방식** | 게임 시작 시 톤 선택 또는 설정에서 언제든 전환 가능 |
| **데이터 구조** | 씬 JSON의 `substitutions`에 `tone_casual`(구어체)과 `tone_classic`(고전체) 두 벌의 대사를 모두 포함 |

### 2.9 저장 시스템 (Password/Code)

| 결정 | 내용 |
|------|------|
| **방식** | 암호(Password) 시스템 - 각 천(Heaven) 도달 시 고유 암호를 부여 |
| **암호 설계** | 해당 천계의 핵심 키워드를 암호로 사용 (예: 월구 → "피카르다", 태양천 → "토마스") |
| **복습 효과** | 암호를 기억하는 행위 자체가 원작의 핵심 인물/개념을 자연스럽게 복습하는 장치 |
| **재시작 시** | 게임 시작 화면에서 암호 입력 → 해당 천부터 이어서 진행 (이전 선택 기록은 기본값으로 초기화) |
| **레트로 감성** | 고전 게임의 스테이지 패스워드 방식을 계승하여 향수 자극 |

### 2.10 타이틀 화면

| 결정 | 내용 |
|------|------|
| **스타일** | 미니멀 - 제목과 암호 입력칸만 표시하는 극도로 간결한 시작 화면 |
| **구성 요소** | 작품 제목 (예: "신곡 - 천국편") + 암호 입력 프롬프트 (빈 입력 시 처음부터 시작) |
| **설정 진행** | 톤 선택(구어체/고전체), 모드 선택(Full/Quick/Demo) 등은 게임 진입 후 대화 형태로 동적 질문 |
| **의도** | 첫 인상을 깔끔하게 유지하고, 설정 과정 자체도 게임의 일부처럼 자연스럽게 느끼도록 설계 |

### 2.11 최종 결과 화면 (엔딩)

| 결정 | 내용 |
|------|------|
| **형식** | 여정 요약 스크롤 - 전체 여정을 빠르게 한 줄씩 스크롤하며 복기 |
| **내용** | 각 천의 이름, 핵심 선택, 영혼 수치 변화를 간결하게 나열 |
| **개인화 해석** | 플레이어의 선택 패턴을 분석하여 "당신은 ~한 순례자입니다"와 같은 성향 해석을 매번 새롭게 생성 |
| **성향 유형 예시** | "의심하되 끝내 믿음에 도달한 탐구자", "직관으로 빛을 좇은 신비주의자", "모든 영혼의 이야기에 귀 기울인 공감의 순례자" 등 |
| **리플레이 가치** | 다른 선택을 하면 다른 성향 결과가 나오므로 재도전 동기 부여 |

## 3. 기술 아키텍처

### 3.1 기술 스택

| 구분 | 기술 | 비고 |
|------|------|------|
| **1차 빌드 (현재)** | Rust 단일 네이티브 바이너리 | 터미널 실행, 수백 KB 목표 |
| **2차 확장 (예정)** | HTML5 + Single-file JS (웹) | 동일 시나리오 데이터를 웹 렌더러로 리팩터링 |

### 3.2 엔진 / 팩 분리 구조

```
project/
├── engine/              # Rust 게임 엔진 (렌더링, 입력, 상태관리)
│   └── src/
│       ├── main.rs
│       ├── loader.rs         # 팩 YAML/JSON 로딩
│       ├── renderer.rs       # 카드 프레임 렌더링
│       ├── state.rs          # 게임 상태 관리
│       └── progression.rs    # 진행 구조 해석 (linear/growth/episodic)
├── packs/               # 팩 데이터 (작품별 완전 독립)
│   ├── paradiso/             # 단테 · 신곡 천국편
│   │   ├── pack.yaml              # 팩 설정 (게임의 정체성)
│   │   └── scenes/                # 씬 데이터
│   │       ├── heaven_01_scene_01.yaml
│   │       └── ...
│   ├── demian/               # 헤세 · 데미안
│   │   ├── pack.yaml
│   │   └── scenes/
│   └── tolstoy_stories/      # 톨스토이 · 단편집
│       ├── pack.yaml
│       └── scenes/
└── tools/               # 빌드 / 검증 스크립트
    └── validate.sh      # is_interpreted 태그 검증 도구
```

### 3.4 원작 파괴 방지 검증 프로세스

1. 시나리오 작성 시 개인 해석이 반영된 씬에는 `"is_interpreted": true` 태그를 **의무적으로** 부착한다.
2. 빌드 전 `tools/validate.sh` 스크립트가 모든 씬 파일을 스캔하여 `is_interpreted: true`인 씬 목록을 출력한다.
3. 기획자(사용자)가 해당 목록을 **명시적으로 승인**해야만 빌드가 진행된다.
4. 승인되지 않은 `is_interpreted` 씬이 포함된 빌드는 **자동 차단**된다.

### 화면 구성 영역

| 영역 | 위치 | 내용 |
|------|------|------|
| **천계 표시** | 프레임 최상단 | 현재 도달한 하늘(Heaven)의 이름 |
| **통합 씬 영역** | 카드 내부 전체 | 아스키 배경 + 화자 형상 + 대화 텍스트가 하나의 그림으로 결합. 화자 옆에 말풍선 형태로 대사 배치 |
| **선택지 영역** | 하단 구분선 아래 | 번호 선택지 (감성적 키워드 어조 적용) |
| **영혼 수치** | 우하단 | 영혼의 빛 게이지 (시각적 바 형태) |

### 4.2 정식 화면 레이아웃 (78 x 40 고화질 시네마틱 프레임)

터미널 멀티플렉서(`ScreenBuffer`) 구조의 몰입감을 극대화하기 위해 **40줄 고화질 시네마틱 프레임**을 채택하며, 고전 어드벤처 게임의 **인물 중심 좌우/중앙 배치 문법**을 적용합니다:

```
╔════════════════════════════════════════════════════════════════════════════╗
║  HEADER (Row 0..2) : 팩 제목 (좌) + 막/씬 이름 (우) (Row 1)                ║
╠════════════════════════════════════════════════════════════════════════════╣
║                                                                            ║
║  SCENE (Row 3..25, 23줄 초대형 캔버스)                                     ║
║  • 대화/갈등 씬: [좌측 화자] ──────── 대립/교감 ──────── [우측 화자]         ║
║  • 독백/성찰 씬: ──────────── [중앙 핵심 인물/상징] ────────────            ║
║  • 배경/분위기 : 고밀도 명암 램프(█▓▒░) 및 외곽선(─│╱╲) 입체 연출         ║
║                                                                            ║
╠══════════════════════════════════════════╤═══════════════════════════════╣
║  DIALOGUE (Row 27..34, 8줄, 좌측 55%)    │  STATUS (Row 27..34, 8줄, 우측 45%)║
║  화자별 대사 (스마트 들여쓰기)           │  수치 게이지, 진행도, 문체, 모드  ║
╠══════════════════════════════════════════╧═══════════════════════════════╣
║  CHOICE (Row 35..39, 4줄) : 선택지 목록 + "선택 번호 입력 ▶"               ║
╚════════════════════════════════════════════════════════════════════════════╝
```

### 영역별 규격 및 고전 게임 인물 배치 규칙:

| 영역 | 높이 | 폭 (컬럼) | 화면 역할 및 연출 규칙 |
|:---|:---:|:---:|:---|
| **1. HEADER** | 2줄 | 78 (100%) | 팩 타이틀과 현재 챕터 이름 고정 표시 |
| **2. SCENE** | **23줄** | **74 (Col 2..75)** | **초대형 고해상도 아스키 캔버스**<br>• **대화형 씬**: 좌측에 주인공, 우측에 상대방을 배치하여 시선과 갈등을 직관적으로 연출.<br>• **사색형 씬**: 알, 거울, 박, 십자가 등 핵심 상징/인물을 중앙에 배치하여 몰입감 강화. |
| **3. DIALOGUE** | 8줄 | 39 (Col 2..40) | 화자명 접두사 및 2번째 줄 이후 자동 들여쓰기로 가독성 보장 |
| **4. STATUS** | 8줄 | 32 (Col 44..75) | 수치 게이지(`███░░░`), 현재 막, 문체, 모드 현황 표시 |
| **5. CHOICE** | 4줄 | 74 (Col 2..75) | 번호 선택지(1~2) 및 인터랙티브 프롬프트 |

## 4.5 팩 설계 표준 파이프라인 (Pack Design Pipeline)

모든 고전문학 팩은 원작의 서사 훼손을 방지하고 게임적 재미와 완성도를 보장하기 위해 **5단계 표준 파이프라인**을 거쳐 제작됩니다:

```
[단계 1: 원문 서사 정리]        [단계 1-1: 서사 구조 설계]        [단계 2: 아스키 콘티]        [단계 3: 씬 초안]        [단계 4: 정식 게임 팩]
1_story.md               ──>  1-1_story_structure.md   ──>  2_conti.md        ──>  3_scene.yaml   ──>  4_game_scene.yaml
(원작 장별 핵심 줄거리 요약)     (씬 그래프/수치/암호/엔딩 설계)     (78x30 프레임/아스키/대사)    (구동용 프로토타입)       (정식 완성형 YAML 팩)
```

### 5단계 파이프라인 상세

| 단계 | 산출물 | 역할 및 핵심 내용 |
|:---:|--------|-------------------|
| **1단계** | `1_story.md` | **원작 서사 완역 및 핵심 줄거리 요약**<br>• 원작의 전체 장별 흐름과 핵심 명대사/주제 정리 (원작 훼손 금지) |
| **1-1단계** | `1-1_story_structure.md` | **스토리 스트럭처 (서사 구조 설계)**<br>• 진행 구조 타입 선택 (`linear` / `growth` / `episodic`)<br>• 씬 그래프(Scene Graph) 및 분기/대체 씬 경로 정의<br>• 핵심 수치(Metric) 정의 및 선택지별 득실 규칙 수립<br>• 장(Chapter)별 암호(Password) 및 3대 엔딩 성향 분석 프로필 설계 |
| **2단계** | `2_conti.md` | **아스키 아트 콘티 & 대사 초안**<br>• 78컬럼 5영역 카드 프레임(Scene Art 14줄) 중앙 정렬 아스키 아트 스케치<br>• 화자별 대화문(구어체/고전체) 및 선택지 2개 구성 |
| **3단계** | `3_scene.yaml` | **구동 검증용 프로토타입 YAML**<br>• 엔진이 실제로 파싱하고 실행해 볼 수 있는 최소 실행 규격 팩 |
| **4단계** | `4_game_scene.yaml` | **정식 완성형 게임 팩 (Final Pack)**<br>• 74칸 고밀도 박스형 아스키 아트 + 스마트 줄바꿈 대화문 + 메타데이터 완비 |

## 4.7 버전 관리 및 깃허브 커밋 규약 (Git Commit Specification)

프로젝트의 모든 버전 기록은 **개발자의 의도와 문제 해결 과정**을 보존하기 위해 다음 규칙을 엄격히 준수합니다:

1. **언어 원칙**: **반드시 한국어로 작성**한다 (영어 커밋 메시지 금지).
2. **목적 중심 기록 (Why & Solution)**: 단순 행위("추가했다", "수정했다")가 아닌, **"무엇이 안 되거나 부족해서(문제) ➔ 어떤 목적으로 무엇을 어떻게 바꾸었는가(해결)"**의 인과관계를 기술한다.
3. **표준 커밋 템플릿**:
   ```
   <태그>(범위): <해결 목적 한 줄 요약>

   - 문제/배경: 무엇이 안 되거나 한계가 있었는가?
   - 해결/목적: 이를 해결하기 위해 어떤 방식을 취했는가?
   ```
   * 태그 예시: `기능(feat)`, `문서(docs)`, `개선(refactor)`, `수정(fix)`, `테스트(test)`

### 7.3 핵심 데이터 구조 (Rust structs)

상세한 Rust 구조체 정의:

```rust
use serde::Deserialize;
use std::collections::HashMap;

#[derive(Deserialize)]
struct Pack {
    id: String,
    title: String,
    author: String,
    description: String,
    language: String,
    tones: HashMap<String, Tone>,
    world: World,
    structure: Structure,
    modes: HashMap<String, Mode>,
    characters: Characters,
    endings: Vec<Ending>,
    layout: Layout,
}

#[derive(Deserialize)]
struct World {
    metric: Metric,
    chapter_term: String,
    chapter_term_en: String,
    failure: Failure,
    password: Password,
}

#[derive(Deserialize)]
struct Metric {
    name: String,
    name_en: String,
    icon: String,
    max: i32,
    initial: i32,
    description: String,
}

#[derive(Deserialize)]
struct Scene {
    scene_id: String,
    act: u32,
    act_name: String,
    title: String,
    theme: String,
    message: String,
    is_interpreted: bool,
    #[serde(default)]
    is_transition: bool,
    scene_art: Vec<String>,
    dialogue: HashMap<String, Vec<DialogueLine>>,
    substitutions: HashMap<String, HashMap<String, String>>,
    #[serde(default)]
    choices: Vec<Choice>,
    #[serde(default)]
    next_scene: Option<String>,
}

#[derive(Deserialize)]
struct Choice {
    id: String,
    text: HashMap<String, String>,
    virtue_change: i32,
    next_scene: String,
}
```

### 7.4 게임 루프 의사코드

```
main():
  pack = load_pack(pack_path)
  state = GameState::new(pack)
  show_title_screen(pack)
  
  password = get_password_input()
  if password:
    state.jump_to_chapter(password)
  
  tone = ask_tone_preference()
  mode = ask_mode_preference()
  state.set_tone(tone)
  state.set_mode(mode)
  
  loop:
    scene = state.current_scene()
    clear_screen()
    render_card_frame(scene, state)
    
    if scene.is_transition:
      wait_for_any_key()
      state.advance_to(scene.next_scene)
    else:
      choice = get_choice_input(scene.choices)
      state.apply_choice(choice)
      state.record_choice(scene, choice)
      
      if state.check_failure():
        show_failure_message(pack, scene)
        state.return_to_checkpoint()
      else:
        state.advance_to(choice.next_scene)
    
    if state.is_game_over():
      break
  
  show_ending_screen(state)
```

### 7.5 렌더러 상세

렌더러 동작 방식:
1. crossterm을 사용하여 화면 지우기 (Clear screen)
2. 터미널 폭 계산 (감지 실패 시 78로 폴백)
3. 위에서 아래로 각 영역 그리기:
   - Header: 이중선 박스 상단 + 타이틀 라인
   - Scene: scene_art 내의 변수 치환, 폭에 맞게 패딩
   - Dialogue|Status: 세로 구분선이 있는 좌우 컬럼
   - Choice: 번호가 있는 선택지 목록, 입력 프롬프트 표시
4. 템플릿 변수 치환: {var_name}을 substitutions[current_tone]의 값으로 교체
5. 수치 바 렌더링: current_value/max에 기반하여 채워진 블록(█)과 빈 블록(░)으로 표시
